# Technical and on-page

The scanner checks presence and plumbing. Wording quality is judged by you.

## Titles and descriptions

- Unique per indexable page, generated from page data rather than a shared
  default (META-003/004, HTML-TITLE-DUP).
- Lead with what the page is about; brand at the end via a template. About
  50-60 characters is a rough lint only: Google truncates by pixel width and
  rewrites titles that are long, stuffed, generic ("Home") or out of line with
  the H1 (title-link guidance). Park pure length warnings unless truncation
  visibly hurts a priority page.
- Patterns by page type (coreyhaines31 `title-tags.md`):

| Page type | Pattern |
|---|---|
| Product / feature | `[Category] for [Audience] \| Brand` |
| Pricing | `Brand Pricing: Plans and Costs` |
| Comparison | `[A] vs [B]: [the deciding difference]` |
| How-to / guide | `How to [Task]` |
| Definition | `What Is [Term]? [Short payoff]` |
| Article | `[Article title] \| Brand` |

- Only promise a year, "free" or a number if the page delivers it.
- Descriptions: a specific summary of the page in roughly 150-160 characters,
  not the title repeated, no stock CTA appended by a template to every page.
  Google may replace it with page text; it affects clicks, not ranking.
- Remove scaffold defaults: "Create Next App", "Generated by create next app",
  the Vite package name, "React App" (META-002).
- `meta keywords` is ignored by Google (META-022).

## Headings

One descriptive main heading per page that matches the title's topic, then a
logical H2/H3 outline. Multiple `<h1>` elements are valid HTML; flag them only
when the main topic becomes ambiguous (HTML-H1-MULTI is info). Headings
phrased as the questions people ask help both readers and answer engines.

## Images

- `alt` on meaningful images describing the content; `alt=""` on decorative
  ones (IMG-001; small SEO effect, real accessibility effect).
- Intrinsic `width`/`height` or CSS `aspect-ratio` to prevent layout shift
  (IMG-002).
- The LCP (hero) image loads eagerly with high fetch priority; everything below
  the fold is lazy (IMG-004). Next.js 16: `fetchPriority="high"` or
  `loading="eager"` (`priority` is deprecated).
- Modern formats (AVIF/WebP) and responsive `srcset`/`sizes`; framework image
  components handle this.
- Descriptive file names help image search.

## Open Graph

`og:title`, `og:description`, `og:image` (absolute URL, about 1200x630),
`og:url`, `twitter:card`. Not a ranking factor, but chat apps, social networks
and AI assistants use them for link previews. In Next.js prefer
`opengraph-image` files and spread shared `openGraph` objects (see
`stack-nextjs.md#metadata-inheritance`).

## Structured data

JSON-LD is Google's preferred format. Rules:

- Describe only content that is visible on the page; markup that misrepresents
  content can earn a manual action.
- Server-render it (SD-005). Google can read JS-injected JSON-LD but recommends
  initial HTML for time-sensitive types such as Product, and many AI fetchers do
  not run JS.
- Escape `<` when serialising (SD-002).
- Include `@context` (SD-006) and absolute URLs.
- Validate with the Rich Results Test (Google features) and the Schema Markup
  Validator (syntax).

Which types still earn Google rich results (as of 2026-11; check the
structured-data gallery before promising one):

| Use freely when true | Keep only if another consumer needs it | No Google rich result |
|---|---|---|
| Organization, LocalBusiness, WebSite, BreadcrumbList, Article/BlogPosting/NewsArticle, Product/Offer (+ merchant listing fields), Review/AggregateRating (not self-serving), Event, JobPosting, VideoObject, Recipe, Course list, SoftwareApplication, ProfilePage, DiscussionForumPosting, QAPage, Dataset (Dataset Search) | FAQPage (rich results retired for all sites on 2026-05-07; harmless when it matches visible Q&A) | HowTo (2023), SpecialAnnouncement, ClaimReview, VehicleListing, EstimatedSalary, LearningVideo, CourseInfo (2025) |

Starting set for most sites:

| Page | Types |
|---|---|
| Home | Organization (name, url, logo, verified `sameAs`), WebSite |
| Nested pages | BreadcrumbList |
| Article template | Article/BlogPosting: headline, author (Person with url), datePublished, dateModified, image |
| Product template | Product + Offer (price, currency, availability) |
| Author pages | ProfilePage / Person |

Google states structured data is not required to appear in AI Overviews or AI
Mode. Treat it as context that helps machines parse the page, not as a
citation lever.

## Core Web Vitals

Field thresholds at the 75th percentile: LCP <= 2.5 s, INP <= 200 ms,
CLS <= 0.1 (FID is retired). Code-visible risks the scanner and review can
catch:

- Render-blocking third-party scripts in `<head>` (PERF-001): `async`/`defer`,
  or `next/script` with `afterInteractive`/`lazyOnload`.
- Web fonts without `font-display: swap` (PERF-002): self-host
  (`next/font`, `@fontsource`) or add `display=swap`.
- Lazy LCP image, images without dimensions, late-injected banners and embeds
  without reserved space.
- Large client bundles on content pages (`'use client'` at the top of a page,
  heavy client-only libraries): move interactivity into small client islands.

Field data (CrUX, Search Console) is **not assessable from code**. Ask for a
PageSpeed Insights report, or run Lighthouse locally as a lab proxy and label it
as lab data.
